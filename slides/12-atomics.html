Atomics are Slow

Avoid them, batch them, or skip them where the hardware allows

The cost of Atomics

plain read
Atomics.load
plain write
Atomics.store

On x86 an Atomics.load is a plain MOV. The cost is the builtin call and the reordering the JIT is no longer allowed to do. Stores are sequentially consistent: a full barrier.

Batch, don't spam

// BAD: publish every message
for (const msg of batch) { write(ring, msg); Atomics.store(state, WRITE, pos) }

// GOOD: plain writes, publish once
for (const msg of batch) write(ring, msg)
Atomics.store(state, WRITE, pos)
Atomics.store × 100
plain × 100 + one Atomics.store

That's what the ring buffer does: plain writes into the data region, one Atomics.store to publish the write position.

Real world: writer.cork()

writer.cork(() => {
  for (const msg of messages) {
    writer.writeSync(msg.length, write, msg)   // plain memcpy, no barrier
  }
})
// outermost uncork → a single Atomics.store of the write index

Uncorked writes are already batched per microtask; corking just makes the batch boundary explicit.

Waking the other side

Atomics.wait / waitAsyncZero CPU while idle, but OS scheduling adds µs of wake-up latency.
Spin with Atomics.pause()Lowest latency, burns a core. Tell the CPU you're spinning.
Only notify when someone waitsAtomics.notify with no waiters still costs 21.8 ns. Keep a “waiting” flag and check it.
// a load instead of a 21.8 ns notify
if (Atomics.load(state, READER_WAITING)) Atomics.notify(state, WRITE)

Memory ordering: x86 vs ARM64

x86 (total store order)Stores become visible in program order and 32-bit accesses are atomic. A reader can get away with plain loads.
ARM64 (weakly ordered)Loads can be reordered. The reader needs an Atomics.load (acquire) of the write index before reading the data. That includes Apple Silicon and Graviton.

Minimum correct protocol everywhere: plain data writes → Atomics.store of the index; Atomics.load of the index → plain data reads.
