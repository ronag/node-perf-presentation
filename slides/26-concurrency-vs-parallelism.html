Concurrency vs Parallelism

Latency vs throughput, and the cost of both

Two different goals

Concurrency: interleaving
1 core
Goal: latency. Don't block, switch while waiting on I/O. Event loop, async/await.
Parallelism: simultaneous
core 1
core 2
core 3
Goal: throughput. Do more work per second. Workers, processes.

The hidden costs

Both add absolute overhead. Sync and single-threaded is the cheapest unit of work.

Concurrency overhead~74 ns per await · microtask queue · async context
Parallelism overhead~0.9 µs per postMessage, ~27 ns via a ring buffer · cache pollution · a heap and GC per thread · Atomics and OS scheduling

benchmarks/async-overhead.mjs · cross-thread.mjs (64 B messages) · EPYC 9355P · Node 26.10

CPU caches: the real bottleneck

One threadData stays in L1/L2 (~1–4 ns), hot and fast.
Many threadsThey evict each other's lines from shared L3 (~10–40 ns), shared data causes false sharing, and more threads ≠ more throughput.

When to use what

Stay single-threadedCPU work under 1 ms, hot data in cache, per-request latency matters most.
Concurrency (async)Waiting on network, disk or DNS; many connections.
Parallelism (Workers)CPU work over ~40 ms (1–40 ms: chunk it and yield), independent state, and a gain that outweighs communication.

Default to single-threaded. Add async for I/O. Reach for Workers when the CPU work is big enough to pay for them, and measure to prove it.
