Most objects die young. The young generation is collected often and cheaply; the old generation rarely and expensively.

The generational hypothesis

  • Most objects die young: allocated, used briefly, discarded.
  • Scavenge copies the few survivors; the garbage costs nothing.
  • Survive two scavenges and you are promoted to the old generation.
  • Mark-compact walks every live object in the old generation.

Keep objects short-lived, or truly long-lived. The worst case is medium-lived: promoted, then dead.

What makes GC expensive

// BAD: retained → promoted → traced on every major GC
cache.set(data.id, { ...data, processed: true })

// GOOD: short-lived, dies in the young generation
return transform(data)

// BEST: no allocation at all
reusable.buffer = data.buffer; reusable.offset = data.offset
return handle(reusable)

GC impact on latency

~1–3 msscavenge: usually fine
10–100+ msmark-compact: the p99 killer

Caching reduces allocation but creates long-lived objects the GC traces on every major collection, even if you never touch them again. Choose the trade-off deliberately.

Less visible ≠ free

Modern V8 does most GC work on background threads. You may not see event-loop lag, but:

  • GC threads compete for CPU cores with your application.
  • Tracing pollutes CPU caches and evicts your hot data.
  • More live objects means more memory bandwidth spent on GC.
  • On a shared host, one process's GC load slows all the others.

Object pooling: trade-offs

Reuse = fewer allocationsNo young-generation churn, no promotion.
Large pool = large old generationEvery pooled object is traced on every major GC, even if idle.
function acquire () { return pool.pop() ?? new Obj() }

function release (obj) {
  if (pool.length < 1000) pool.push(obj)   // bounded; let the GC take the overflow
}

Object pooling: pitfalls

Unbounded poolA memory leak that also makes every major GC slower.
Constantly overflowing poolWorse than no pool: you pay for tracing the pool and for allocating the overflow.
Right-sized poolSize it to actual reuse, and measure.

Essential GC flags

--max-semi-space-size=64    # MiB per semi-space; default scales with RAM, ≤ 32 in V8 14
--max-old-space-size=8192   # MiB; default 2 GiB (4 GiB with ≥ 15 GiB RAM)
--trace-gc                  # one line per GC: kind, heap before → after, pause
--expose-gc                 # global.gc(): benchmarks and off-peak collection

Defaults follow physical or cgroup memory. The young generation takes about 3× the semi-space size.
