Step 1: a better allocator

LD_PRELOAD=/usr/local/lib/libmimalloc.so MIMALLOC_PURGE_DELAY=1000 node app.js   # no rebuild
JSON.stringify escaped strings 1.8 MiB
Buffer.allocUnsafe 256 KiB chunk churn
process startup

The purge delay is a dial: a 1 s delay is fast, but after 512 MiB of Buffer churn it keeps 579 MiB resident vs 63 MiB with glibc. Purging on free saves RSS and costs throughput.

Geomean over 58–60 workload metrics: +1.4% (RSS after churn, 9× higher, left out) · EPYC 9355P · Node 26.10 · median of 8 interleaved runs

Step 2: link-time optimization

./configure --enable-lto   # inline and optimize across Node, V8 and every dependency
gzip level 1, 1 MiB
JSON.parse small object (~250 B)

On its own it's a wash: inlining across files cut JSON.parse's instructions by 3%, but the bigger hot path misses the instruction cache 29× more often, which eats the gain. PGO lays hot code out again (step 5).

Geomean over 58–60 workload metrics: +0.6% · our Clang 20 build vs the official binary: +0.1% (the control) · EPYC 9355P · Node 26.10

Costs: ~5.5 GiB RSS per link and a slow rebuild loop. perf stat, small-object JSON.parse, Clang 20 without vs with LTO: instructions per parse −3.3% (8,849 → 8,554), IPC 5.35 → 5.15, front-end idle 2.6% → 7.1%, L1 I-cache misses 0.24 → 6.8 per parse. On the 1.8 MiB escaped payload the instruction count is identical and IPC drops 2%: layout, not codegen.

Step 3: compile for the CPU you run on

-march=znver5 -mtune=znver5 -mno-gather   # Zen 5: AVX-512, VNNI, GFNI, VPCLMULQDQ
Buffer.swap16 8 KiB
JSON.parse GeoJSON
gzip level 1, 1 MiB
process startup

-mtune is free; -march is a contract: Zen 5 only, SIGILL anywhere else. Portable: x86-64-v3 / -v4.

We build with -mno-gather. Without it, Clang 23 turns zlib's CRC32 loop into AVX-512 gathers, slow on Zen: gzip 2.40 → 1.59 GiB/s. Compiler upgrades can regress: benchmark every step.

Geomean over 58–60 workload metrics: +2.9% · EPYC 9355P · Node 26.10 · median of 8 interleaved runs

Step 4: a newer compiler

CC=clang-23 CXX=clang++-23 ./configure   # the official 26.10 binary: Clang 20.1
JSON.parse small record
JSON.parse primitives 1 MiB

On its own: +0.7% geomean. A newer compiler isn't automatically faster: measure it (see the gather note in step 3).

Geomean over 58–60 workload metrics: +0.7% · EPYC 9355P · Node 26.10 · median of 8 interleaved runs

Why -mno-gather: Clang 23's SLP vectorizer turns zlib's CRC32 table loop into AVX-512 gathers, which are microcoded and slow on Zen. LLVM's cost model treats "has AVX-512" as "has fast gathers" (upstream: PR #206506 closed unmerged, PR #212997 open). -fno-slp-vectorize also fixes it but turns SLP off everywhere. Even without gathers, Clang 23 runs that loop ~10% slower than Clang 20. Trap: configure doesn't pass your CFLAGS to V8, so inject flags with a compiler wrapper and check they landed (we count zmm and vpgather instructions in the binary).

PGO: you get what you train

It optimizes what the training corpus exercises, and can pessimize what it doesn't.

Chart: this A/B, EPYC 9355P, Node 26.10 · swap16: an earlier Clang IR-PGO experiment, Node 26.5 (not in results/)

Weight the corpus like production traffic. A JSON-only profile made escaped strings slower. Retrain on every Node bump; V8's Torque builtins aren't reached by Clang PGO.

Pointer compression: the fine print

4 GiB heap per isolateEach Worker gets its own cage, so a process with Workers can still use more in total.
A different addon ABIPrebuilt V8-API (NAN) addons crash: rebuild them against your headers (--nodedir). N-API addons work unchanged.
Some workloads get slowerJSON.stringify escaped strings 1.8 MiB −34%, JSON.stringify small record −10%. Measure yours.

Memory is what you pay for. This is the single biggest memory win we have, and production runs it.

Step 7: customize V8

A ~90-line V8 patch adds v8::ArrayBufferView::CopyArrayBufferViewBytes, so buf.copy() copies between views without materializing their ArrayBuffers.

It's your runtime: small, targeted patches (and upstreaming them) are fair game. Rebase them on every release, and run the full test suite.

How to build it

# cc-wrap adds -O3 -march=znver5 -mtune=znver5 -mno-gather, plus -fprofile-* from NODE_PGO
# (Node's own --enable-pgo-* is GCC-only)
ENV CC=/usr/local/bin/cc-wrap CXX=/usr/local/bin/c++-wrap
RUN git apply v8-copy-array-buffer-view-bytes.patch

RUN ./configure --enable-lto --experimental-enable-pointer-compression \
 && NODE_PGO=generate make -j"$(nproc)"                     # 1. instrumented build
RUN ./out/Release/node train.mjs                            # 2. run the corpus (120 s)
RUN llvm-profdata merge --weighted-input=16,json.profdata … -o node.profdata
RUN make distclean && ./configure --enable-lto … \
 && NODE_PGO=use make -j"$(nproc)"                          # 3. optimized build
RUN make test-ci                                            # it's your runtime now: test it

Two full compiles plus training: hours, not minutes. Cache them as Docker layers and rebuild per Node release.
