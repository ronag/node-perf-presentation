Step 1: tune the runtime: a better allocator

LD_PRELOAD=/usr/local/lib/libmimalloc.so MIMALLOC_PURGE_DELAY=1000 node app.js   # no rebuild
B_STEP_MIMALLOC_ROWS

The purge delay is a dial: a 1 s delay is fast, but B_MIMALLOC_RSS. Purging on free saves RSS and costs throughput.

Step 2: a newer compiler

CC=clang-23 CXX=clang++-23 ./configure   # the official 26.10 binary: Clang 20.1, no LTO
B_STEP_CLANG_ROWS

Trap: Node's configure doesn't pass your CFLAGS to V8. Inject flags with a compiler wrapper, and check that they landed.

Step 3: link-time optimization

./configure --enable-lto   # inline and optimize across Node, V8 and every dependency
B_STEP_LTO_ROWS

Costs: link time (~5.5 GiB RSS per link) and a slower rebuild loop. Link with BFD; LLD and gold broke a SEA test for us.

Step 4: compile for the CPU you run on

-march=x86-64-v3 -mtune=znver3     # AVX2 · BMI2 · FMA · F16C
B_STEP_MARCH_ROWS

-mtune is free; -march is a contract. On a CPU older than Haswell / Zen 1 the binary dies with SIGILL. Watch generic VM CPU models.

−93%buf.swap16() when the training corpus never called it: its loop was optimized for size
+1,457%after adding a few swaps to the corpus (same source)
  • Train on what production runs: weight the corpus like your traffic.
  • A narrow corpus overfits: a JSON-only profile made escaped strings slower.
  • Retrain on every Node version bump. V8's Torque/CSA builtins aren't reached by Clang PGO.

Pointer compression: the fine print

4 GiB heap per isolateEach Worker gets its own cage, so a process with Workers can still use more in total.
A different addon ABIPrebuilt .node binaries for stock Node crash: rebuild native addons. N-API addons work; old V8-API addons don't.
Some code gets slowerDecompressing pointers costs a little on pointer-heavy hot loops: B_PC_COST

Memory is what you pay for. This is the single biggest memory win we have, and production runs it.

Step 7: customize V8

A 60-line patch adds v8::ArrayBufferView::CopyArrayBufferViewBytes, so Buffer.copy copies between views without materializing their ArrayBuffers.

B_STEP_V8_ROWS

It's your runtime: small, targeted patches (and upstreaming them) are fair game. Rebase them on every release, and run the full test suite.

The same change is proposed upstream as nodejs/node#63892.

How to build it

# compiler wrapper adds: -O3 -march=x86-64-v3 -mtune=znver3 [-fprofile-generate | -fprofile-use=…]
ENV CC=/usr/local/bin/cc-wrap CXX=/usr/local/bin/c++-wrap
RUN git apply v8-copy-array-buffer-view-bytes.patch

RUN ./configure --enable-lto --experimental-enable-pointer-compression \
 && NODE_PGO=generate make -j"$(nproc)"                     # 1. instrumented build
RUN ./out/Release/node train.mjs                             # 2. run the corpus (120 s)
RUN llvm-profdata merge --weighted-input=16,json.profdata … -o node.profdata
RUN make distclean && ./configure --enable-lto … \
 && NODE_PGO=use make -j"$(nproc)"                          # 3. optimized build
RUN make test-ci                                             # it's your runtime now: test it

Two full compiles plus training: hours, not minutes. Cache them as Docker layers and rebuild per Node release.
