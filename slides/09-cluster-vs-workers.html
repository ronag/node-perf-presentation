Cluster vs Workers w/ reusePort

Scaling Node.js across cores

The cluster module

import cluster from 'node:cluster'

if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) cluster.fork()
} else {
  http.createServer(handler).listen(3000)
}

Worker threads + reusePort

const n = availableParallelism()
for (let i = 0; i < n; i++) new Worker('./http-worker.js')

// http-worker.js: every Worker binds the same port
http.createServer(handler).listen({ port: 3000, reusePort: true })
Kernel load balancingSO_REUSEPORT: the OS distributes connections. No primary bottleneck.
Shared memoryWorkers share a process: SharedArrayBuffer + Atomics.
eBPF steeringAttach a BPF program to the socket group to steer by CPU, session or load.

Node ≥ 22.12 / 23.1. Linux 3.9+, FreeBSD 12+ and a few others; it throws on macOS and Windows.

How the kernel picks: every Worker has its own listening socket in one SO_REUSEPORT group. For each new connection the kernel hashes the 4-tuple (source IP, source port, destination IP, destination port) and picks socket = hash mod group size. No shared accept queue, no primary, no thundering herd. But it balances connections, not load: a long keep-alive connection sticks to one Worker, a blocked Worker still gets its share of new connections, and a few connections can land unevenly (4 connections on 4 Workers: all on different Workers only 9% of the time). Adding or removing a Worker reshuffles the mapping. An eBPF SK_REUSEPORT program can override the choice: by CPU, by session, or least-loaded.
