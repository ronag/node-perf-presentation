Benchmarks Lie

V8 is smarter than you. So is the CPU.

V8 works against your benchmark

Dead code eliminationA result that's never used gets deleted, and you measure nothing.
Constant foldingInputs that never change get precomputed. Randomize them.
JIT warm-upWithout warm-up you measure the interpreter, not TurboFan.
DeoptimizationNew shapes mid-run and you measure the deopt, not the code.
Escape analysisAn object that never escapes is never allocated. “0 B” can mean “optimized away”.
GC outside the timermitata's .gc('inner') collects between samples, so GC time isn't in the number.

Keep the work alive

import { bench, do_not_optimize } from 'mitata'

bench('sum', () => {
  let sum = 0
  for (let i = 0; i < n; i++) sum += data[i]   // inputs vary per run
  do_not_optimize(sum)                          // result is observed
})

The CPU cheats too

Branch predictionA loop that always takes the same branch is “memorized”. Production branches aren't.
CachesBenchmark data fits in L1/L2. Production data doesn't: 2 ns/op becomes 20.
Out-of-order executionTight loops overlap independent work far better than real call chains.

A benchmark is the best case for both V8 and the CPU. Production is the worst case.

Big-O counts steps, not cache misses

intrusive array, swap-remove · O(1)

Set delete + add · O(1)
linked list with wrapper nodes + Map · O(1)
indexOf + splice · O(n)

Four O(1) structures, 10× apart: allocation, hashing and pointer chasing are the constants Big-O hides.

Rules for trustworthy benchmarks

  1. Consume results (do_not_optimize) and randomize inputs.
  2. Warm up, then measure what TurboFan produces.
  3. Use production sizes: 100 MB of data, not 1 KB.
  4. Watch allocation and GC, not just time.
  5. Use production hardware: pinned cores, the real OS. Every number here: AMD EPYC 9355P, Linux, Node 26.10, Docker.
  6. Validate against production. If they disagree, trust production.
