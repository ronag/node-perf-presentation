Callbacks w/ Opaque vs Closures

Avoiding hidden allocation costs

The hidden cost of closures

Escaping closure: allocates per call
function sendLater (ctx) {
  setTimeout(() => {
    ctx.connection.write(ctx.payload)
  }, 5000)
}
// new function object + context
// kept alive (and promoted) for 5 s
Static callback + opaque data
function onTimeout (ctx) {
  ctx.connection.write(ctx.payload)
}
function sendLater (ctx) {
  setTimeout(onTimeout, 5000, ctx)
}
// the callback is a static reference

Node's setTimeout(fn, ms, arg) still allocates an args array. The win is biggest in APIs designed for (fn, opaque).

Why this matters at scale

1,000 closures
static function + opaque

A closure keeps its scope's context alive, including every variable any closure in that scope captures. Long-lived ones (timers, listeners, queued work) survive scavenges, get promoted, and are traced on every major GC.

A function queue: closures vs a flat array

closureQueue.push(() => handler(ctx))   // closure queue: one allocation per push

class FlatQueue {                  // flat queue: [fn, opaque] pairs in one array
  q = []; n = 0
  push (fn, opaque) { this.q[this.n++] = fn; this.q[this.n++] = opaque }
  drain () {
    const q = this.q
    for (let i = 0; i < this.n; i += 2) {
      const fn = q[i], opaque = q[i + 1]
      q[i] = q[i + 1] = undefined
      fn(opaque)
    }
    this.n = 0                     // keep the backing store (length = 0 frees it)
  }
}
queue.push(handler, ctx)           // static function ref: zero allocations
