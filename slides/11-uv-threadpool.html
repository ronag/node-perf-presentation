The libuv Thread Pool

The hidden bottleneck

What uses the thread pool?

// all of these share the SAME pool, 4 threads by default
fs.readFile(path, cb)             // async file I/O
crypto.pbkdf2(pass, salt, …, cb)  // crypto
zlib.deflate(buf, cb)             // compression
dns.lookup(host, cb)              // DNS: also every http.get('host…')

Four slow disk reads and your outgoing HTTP requests stall on DNS. (dns.lookup is capped at half the pool.)

Configuring the pool

UV_THREADPOOL_SIZE=16 node server.js   # read once, at the first pool task
pbkdf2 · 4 threads
pbkdf2 · 16 threads
mixed fs + crypto · 4 threads
mixed fs + crypto · 16 threads

Page-cache fs reads: 348K vs 359K ops/s, no change. More threads help blocking work, not fast work.

benchmarks/uv-threadpool.mjs · EPYC 9355P · Node 26.10

Gotchas

Must be set earlyRead once, at the first pool task: set it in the environment or process.env before that. Maximum 1024.
More ≠ betterMore memory and context switches. Pure page-cache fs can get slower.
Shared across WorkersOne pool per process: 4 Workers × default pool = ~1 thread each.

Why not auto-size it?

nodejs/node#61533 sized the pool to the available parallelism. On a 16 vCPU host:

+281%crypto-heavy route
+89%mixed fs + crypto
−15%pure fs

Closed unmerged: “Just because there are many CPUs in a host, it doesn't mean they are free. Saturating the CPU is worse than queuing I/O tasks.” Size it for your workload.
