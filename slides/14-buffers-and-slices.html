Buffers are Slow: Use Slice

@nxtedition/slice

Why Buffer views are expensive

subarray: a new view per call
for (const msg of messages) {
  parseHeader(msg.subarray(0, 4))
  parseBody(msg.subarray(4))
}
// 2 Uint8Arrays per message
Slice: one object, reused
const s = new Slice()
for (const msg of messages) {
  s.buffer = msg
  s.byteOffset = 0; s.byteLength = 4
  parseHeader(s)
  s.byteOffset = 4
  s.byteLength = msg.length - 4
  parseBody(s)
}   // 0 allocations

Slice: a plain JS object

class Slice {
  buffer      // the backing Buffer
  byteOffset  // start, relative to buffer
  byteLength  // length
}
buf.subarray()A new Uint8Array per call, through the species constructor and argument validation. Cannot be reused.
SliceThree fields on one hidden class. Mutate and reuse.

Node's I/O already speaks (buffer, offset, length): fs.read/write(Sync), buf.copy, buf.toString, buf.write.

Buffer.poolSize: bump it

Buffer.poolSize = 1024 * 1024   // pooled below 512 KiB (default 64 KiB → below 32 KiB)
poolSize 64 KiB (Node 26 default)
poolSize 1 MiB

Node 26.3 raised the default from 8 KiB to 64 KiB. A bigger slab means fewer slab allocations, at the cost of more pinning.

A pool allocator

One big region, power-of-two buckets, freed slots reused, never handed to the GC.

64 B8 B256 Bfree32 B8 B← next
alloc: O(1)Pop a bucket's free list.
free: O(1)Push onto the free list.
realloc in placeSame bucket? Just update the length.

Trade-offs: up to ~50% slack from power-of-two rounding; requests over 256 KiB fall back to Buffer.

Pool allocator: API

import { PoolAllocator } from '@nxtedition/slice'

const pool = new PoolAllocator()  // huge pages if available
const s = pool.realloc(256)       // a PoolSlice
pool.realloc(s, 200)              // same bucket: in place
pool.realloc(s, 0)                // free: slot recycled
