Atomics Are Slow

Avoid them, batch them, or skip them where a stale value is harmless

The cost of Atomics

plain read
Atomics.load
plain write
Atomics.store

On x86 an Atomics.load is a plain MOV. The cost is the builtin call and the reordering the JIT is no longer allowed to do. Stores are sequentially consistent: a full barrier.

Batch, don't spam

// BAD: publish every message
for (const msg of batch) { pos = write(ring, pos, msg); Atomics.store(state, WRITE, pos) }

// GOOD: plain writes, publish once
for (const msg of batch) pos = write(ring, pos, msg)
Atomics.store(state, WRITE, pos)
Atomics.store × 100
plain × 100 + one Atomics.store

That's what the ring buffer does: plain writes into the data region, one Atomics.store to publish the write position. @nxtedition/shared batches for you: one store per microtask (or per 256 KiB).

Waking the other side

Atomics.wait / waitAsyncZero CPU while idle, but OS scheduling adds µs of wake-up latency.
Spin with Atomics.pause()Lowest latency, burns a core. Tell the CPU you're spinning.
Notify only if waitingAtomics.notify with no waiters still costs 21.8 ns. Keep a “waiting” flag and check it.
// check a flag before notifying
if (Atomics.load(state, READER_WAITING)) Atomics.notify(state, WRITE)

Memory ordering: x86 vs ARM64

x86 (total store order)Loads stay in order and stores stay in order, so a stale plain load is late, not wrong. Plain loads are safe only where late is fine (the read index the writer polls). The JIT can still reorder them.
ARM64 (weakly ordered)Loads and stores can both be reordered. Writer: Atomics.store (release) after the data. Reader: Atomics.load (acquire) before it. That includes Apple Silicon and Graviton.

Minimum correct protocol everywhere: plain data writes → Atomics.store of the index; Atomics.load of the index → plain data reads.
